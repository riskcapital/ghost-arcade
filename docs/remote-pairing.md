# LAN remote pairing

Connect Mobile shows a pairing code alongside the QR code. The QR URL contains the code, so scanning it supplies the credential automatically. A phone can instead type the code and WebSocket address. Accepted codes are remembered on the phone. Reset pairing replaces the saved code and disconnects every current remote connection; all phones must pair again. The desktop reconnects using the new code.

The WebSocket and HTTP listeners reject requests without a valid per-install random code. The desktop supplies it too. The code is stored under the desktop profile in `remote-pairing.json`, created with owner-only file permissions, and survives restarts. Reset writes the replacement before revoking the active token; a failed write does not pretend the reset succeeded. If initial profile storage is unavailable, a temporary session code is used. MCP retains its separate enable-time token and loopback binding; only the constant-time comparison helper is shared.

Browser sockets present the credential explicitly; they never authenticate through ambient cookies. HTTP cookies allow the paired mobile page and its assets to load. Cookie-only mutation requests are rejected, and authenticated responses prohibit caching and referrer forwarding. A revoked socket stops handling messages immediately, even if its closing handshake stalls. The existing 10 MB WebSocket message limit and message rate limit remain in place. Authentication does not add transport encryption: this is HTTP/WS on a trusted local network, not an Internet-facing service or protection against a hostile network operator capturing plaintext traffic.

The development server can use `WS_PORT`, `HTTP_PORT` and `GA_REMOTE_BIND_HOST`; the acceptance tests use temporary loopback ports. Desktop packaged ports remain 9001/9002. Startup no longer kills an arbitrary process already using a port. If a listener is busy, resolve the conflict without disrupting the other application. The standalone server accepts `GA_PAIRING_TOKEN` or generates and prints a session code. Browser-only development can pass that code using `?pair=CODE` (optional `ws` and `http` port parameters). Do not share URLs containing your real code.

Validation: real-socket tests cover rejected and accepted handshakes, paired control relay, cookie rules, preflight, revoked connections, old credentials after reset, malformed/escaping asset paths, token persistence and message-size limits. Renderer tests cover token delivery and storage failure. Mac development UI verified the code/QR controls, and an unpaired browser saw the pairing page. Physical phone QR/reconnect, packaged Windows/macOS and venue-network acceptance remain outstanding.

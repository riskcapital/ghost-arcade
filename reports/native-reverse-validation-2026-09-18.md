# Native reverse playback

Local implementation on `codex/clip-transitions`, not a release or Windows runtime qualification.

## Behavior

VJ video speed includes Reverse 0.25x, 0.5x, 1x, 2x and 4x. Reverse launches, restarts, preparation and Fader Start use trim-out. Once holds the first picture; Loop wraps within the trim. Pausing, exact adjacent-frame stepping, seeks and switching back to forward playback share existing transport generations. The selected speed persists in projects. Autopilot counts elapsed reverse transport rather than immediately advancing at trim-out. Browser audio is silent while reversing and can resume when forward playback returns.

HAP reads indexed independent compressed frames. Native inter-frame video decodes a GPU window of up to sixteen pictures and presents it backward. The window, pending decoder frames, presentation ring, retained opening and GPU submissions are included in memory admission. The initial format probe covers only bounded pending outputs; the complete window uses measured allocation bytes and can shrink from sixteen to four pictures when the shared budget is tighter. A reverse opening is retained before preroll is ready: one HAP picture or up to sixteen native pictures. Repeated triggers replay it without render-thread file access. Unsupported software-only playback fails explicitly rather than playing forward at a tiny positive speed.

This is reverse playback, not bounce or beat-phase locking. Those roadmap items remain open. Mapping transport has the native signed-rate capability, but this change adds the new speed choices to VJ controls. Native clip audio, reverse audio and broader long-GOP multi-stream continuous-reverse performance qualification remain open.

## Evidence

- Mac UI: HAP reverse speed selected; Restart begins near the one-second trim-out; Once descends to zero; pause works; saved project reopens with Reverse 0.25x intact.
- Real GPU output comparisons cover HAP, HAP Alpha and HAP Q; decreasing source timestamps, Once endpoint, trimmed reverse loops, warm reverse retriggers, exact reverse stepping and switching direction are exercised. H.264 with B-frames is checked across reverse windows, paused seeks, warm replay/resume, actual endpoint color, and return to forward playback.
- Initial sixteen-stream reverse HAP sample: 59.92 compositor fps, all sixteen tiles visible, zero dropped source frames, underflows, software frames or decoder failures. Same short 1080p60 / 512-pixel atlas / 1 GiB-budget method as the forward HAP benchmark. This sample preceded expansion of native-codec opening retention; HAP also subsequently gained a separately charged opening picture.
- Four 960×540 30 fps Wire Circuit H.264 clips, each with an eight-second GOP, retriggered every 125 ms for eight seconds: the initial three-picture opening reported 751 underflows. Retaining the already-decoded eight-picture opening reduced this to zero across 256 launches, with zero software frames/fallbacks/CPU pixel uploads. Command acknowledgement median 1.54 ms, p95 2.12 ms; acknowledgement is not input-to-display latency. Both reports are retained.

Windows compiler checks pass; Windows GPU playback and physical controller latency are not qualified by these Mac tests. Short cached-file benchmarks do not substitute for a long show, cold storage, 4K multilayer composition or thermal testing.

Continuous four-clip Wire playback then exposed a distinct queue-depth issue: an eight-picture reverse cache with a three-picture presentation ring produced 1,440 hardware frames over 16.01 seconds (approximately 22.5 fps per clip) and 1,199 underflows. Queuing a full reverse window while the preceding GOP decodes corrected this. With the adaptive sixteen-picture window/ring/opening, the same test produced 1,928 hardware frames over 16.01 seconds (approximately 30 fps per clip, including startup/trigger frames) and zero underflows or software uploads. Before/after reports are retained. This is a short four-clip 960×540 test, not a claim about arbitrary long-GOP 4K media.

The sixteen-stream HAP Alpha stress test exposed a compositor scheduling issue shared by forward and reverse playback: a render attempt blocked by the previous GPU frame consumed its scheduled slot, then waited for the next slot even after the GPU became free. Forward comparison measured 52.68 output fps with 72 backpressure skips while source presentation stayed near 60 fps; an idle reverse comparison measured 53.64 output fps. A separate run concurrent with a build measured 41.53 fps and is not an isolated playback measurement. GPU completion now retries a pending frame immediately while preserving the next deadline and the existing single-frame GPU limit. A deterministic regression checks blocked-slot retry, the following deadline and long-stall recovery. Final reverse HAP Alpha measured 59.93 output fps, all sixteen tiles visible, zero underflows/fallbacks/decode failures. Retained reports distinguish attempted backpressure skips from actually lost presentation cadence.

Final sixteen-stream reverse HAP Q measured 59.93 output fps, with zero underflows/fallbacks/decode failures. Across approximately ten seconds, the final HAP Alpha report recorded 0 dropped source frames and HAP Q recorded 8 across all sixteen streams; these are near-60 measurements, not zero-drop guarantees.

Final checks: 35 native playback/transition tests pass with one Windows-only skip; 149 control/audio/persistence/scrubber tests pass; 107 Rust tests pass with six opt-in tests ignored. Desktop and mobile checks have zero errors (1037 and 52 existing warnings respectively). Production web build and Windows compilation pass. The Mac controls were checked through the UI, including save/reopen. The final buffer and scheduler refinements were validated in native GPU tests. The development app was left open on its older running core after the user loaded a different clip; restarting the app loads the final rebuilt core without requiring another build. No commit, push, package or release was made.
